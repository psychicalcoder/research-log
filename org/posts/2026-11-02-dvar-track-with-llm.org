#+TITLE: dvar-track with LLM
#+DATE: <2026-11-02 Mon>
#+DESCRIPTION: Validating overapproximated Emacs Lisp variable dependencies using LLM agents and reproducible evidence

* Problem

dvar-track is an overapproximation tool. It reports hundreds of
suspected dependencies of a function. Some of them can be false
positives. It is not easy to validate the dependencies even though
dvar-track records dependency inheritance paths and call graphs. Our
goal is to find unexpected dependencies or false assumptions about the
default values of dependencies from true positives.

* Validating True Positives is Laborious Work

Proving that a suspected dependency is a false positive is an
undecidable problem. On the other hand, what you need to prove that a
dependency is a true positive is a piece of code that can trigger
behavior changes after modifying the dependency variable. Constructing
evidence is exactly the same as writing tests. Tests can show the
presence of bugs, and evidence can show the presence of dependencies.

This is the domain of LLMs. LLMs are patient and fast, but not
faithful. However, the evidence can be replayed by the evidence
evaluation tool. We trust the tool rather than trusting the LLM.

* What is evidence?

We know ~prin1~ depends on ~print-length~. The evidence is a set of
arguments and two values of ~print-length~, such that when we bind
~print-length~ to these two values, ~prin1~ supplied with those arguments
behaves differently.

#+BEGIN_SRC emacs-lisp
  (let ((print-length 1))
    (prin1 '(1 2 3 4 5 6 7))) ;; print (1 ...)

  (let ((print-length 3)) 
    (prin1 '(1 2 3 4 5 6 7))) ;; print (1 2 3 ...)
#+END_SRC

* Evidence Evaluation Tool 

Emacs being a user-oriented tool, many of the side effects are
UI-related. We cannot just monitor the return value of the function. It
is more complicated. I therefore divide the evaluation into 5 stages.

1. *common setup*: including setting up ~load-path~ and loading packages.
2. *setup*: set up the scenario, such as adding some content to a buffer.
3. *trigger*: an action to trigger the target function, such as a function call or a keyboard macro.
4. *extractor*: extract the side effect from Emacs after triggering the function.
5. *test*: compare the results and validate that they are really different.

*Trigger* will be executed after the evaluation tool binds the value to the variable.

An actual piece of evidence looks like

#+BEGIN_SRC emacs-lisp
  (reproduce
   dvar-repro-common-setup
   (make-reproduce-config
    :varsym 'search-upper-case
    :val1 t
    :val2 nil
    :setup '((message nil)
             (require 'anzu)
             (switch-to-buffer "repro")
             (insert "foo Foo foo Foo\n")
             (goto-char (point-min)))
    :trigger '((execute-kbd-macro
                (kbd "M-x anzu-query-replace RET Foo RET bar RET !")))
    :extractor '(lambda (_config ret)
                  (list :return ret
                        :buffer (buffer-substring-no-properties
                                 (point-min) (point-max))
                        :point (point)
                        :echo (current-message)))))
#+END_SRC

Two values of the target variable ~search-upper-case~ are run in two
isolated ~emacs -Q~ instances. The instances are launched by the
reproduce tool.

** Limitations

1. Timing-related side effects cannot be reproduced.
2. Randomness without a fixed random seed cannot be reproduced.
3. The setup, trigger, and extractor are now generated by LLMs. Now we
   have to trust that the trigger really calls the target function and
   that the dependency will not affect the code in the trigger other
   than the target function.

* Agents

The agentic workflow consists of 1 coordinator agent, and 1 validator
subagent per batch of dependencies.

** Coordinator Agent

The coordinator is the primary agent that communicates with the user.
Users provide a function name ~FN~. The coordinator skips the suspected
dependencies that have been validated, and dispatches the validation
task in batches of 5 dependencies to the validator agents.

It is also responsible for setting up the script to launch a one-time
Emacs instance with the target package loaded for the validators.

After a subagent finishes its job, the coordinator needs to verify the
result in case there is an unexpected runtime error during the
subagent execution, and compose a final report.

** Validator Subagents

For each batch, the coordinator spawns a fresh subagent without the
context of the previous batch. Initially, a validator receives a list
of suspected dependencies and the information of the one-time Emacs
instance script. Then, it performs the validation procedure described
in the dependency validation skill, which will be introduced later.

* Domain Skill

The skill is a ~580-line markdown file that teaches the agent what a
dependency is and how to perform dependency validation.

*** 1. Problem & Semantics

First, define what a real dependency is: a let-binding before calling
the function can change the behavior of the function under some
scenario, illustrated with the ~print-length~ example.

To justify the false positives, it needs to know how dvar-track
overapproximates dependencies and where the false positives come
from. Therefore, I summarized the 5 dependency propagation rules in
the skill.

*** 2. Emacs Interface

Then I teach the agent how to use ~emacsclient --eval SEXP~ to control
Emacs, how to use the inheritance path traversal tool in dvar-track,
and how to read the Emacs Lisp source code with the built-in navigation
facilities of Emacs.

*** 3. Analysis & Classification

In this section, I define the categories of false positives and
describe the steps of validation. I also supply an example of
argument tracking in order to justify the false positives due to
unreachable branches, as I believe it is the major source of false
positives.

*** 4. Output Contract

For false positives, classify them into a category, and describe the
reason. For true positives, provide evidence with the evidence
evaluation tool. I spend roughly 1/3 of the context (of the skill) to
teach the agent how to use the evidence evaluation tool and how to run
a reproduction.

The last thing is to specify the output format, so that the
coordinator and the reproduction run script know where to find the
evidence specification.

* Result

I use OpenCode with the *Deepseek-v4.1-flash-1017* served by the RCP of
EPFL. It is surprising that such a cheap model can correctly
understand the concept of dependencies and construct evidence. 160 out
of 373 suspected dependencies of ~anzu-query-replace~ were diagnosed as
true positives. Although this model is very small, EPFL RCP only
provides roughly 100 tokens per second. It takes 2 minutes to verify a
single true positive. For false positives, there are more things to
analyze, so it takes much longer.

We found that the variable ~query-replace-show-replacement~ was
wrongly documented as /"This variable affects only ‘query-replace-regexp’"/.
It also affects ~query-replace~, which internally doesn't call
~query-replace-regexp~.

I've also tried using Claude Sonnet to construct evidence and using
Claude Opus 5.5 to convert that evidence to the evidence evaluation
spec. It also works well.
